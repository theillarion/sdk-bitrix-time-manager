# Bitrix Time-manager — Python API

Асинхронная Python-библиотека и консольные команды для Time-менеджера
`your-portal.example`. Работает через REST вебхук владельца: все операции
ограничены этим сотрудником. Python 3.11 и новее.

Поддерживает:

- создание удалённой работы с датой, началом, окончанием и комментарием;
- создание обычного рабочего дня вручную;
- добавление учета времени к существующему дню: описание, часы, минуты, договор;
- чтение рабочего дня, его учета времени и удалёнки; поиск договоров и шаблонов;
- предварительную проверку запросов, обнаружение дублей и журнал операций.

Автоматическая проверка на реальном портале подтвердила вебхук, схему полей,
поиск и предварительную проверку всех трёх операций, без отправки запросов
создания. Результат сохранён в [verification.json](verification.json).
Позднее пользователь вручную подтвердил
успешное создание удалёнки на будущую дату и учета времени на существующий день.
Точное время работы роботов и граничные правила допустимых дат ещё требуют проверки.

## Границы проекта

Это отдельный пакет `bitrix-time-manager`: Python SDK и команда `bitrix-time`.
Приложения вызывают SDK напрямую через Python API.
Telegram-бот и его требования находятся в отдельном проекте
`python-bitrix-time-manager`; SDK не зависит от Telegram.

Пакет можно устанавливать из этого каталога или из Git с фиксацией конкретного
коммита. Публикация в PyPI для подключения к боту не требуется.

## Документация SDK

Технические требования, use-case, чек-листы и известные ограничения
собраны в [docs](docs/README.md). Они охватывают публичный Python API и CLI.
Приложение, включая Telegram-бота, вызывает методы SDK напрямую в своём процессе.

## Установка и настройки

SDK выделен в отдельный проект 8 октября 2026 года. Локальные `.env` и
`.state/operations.sqlite3` перенесены вместе с ним; виртуальное окружение
создаётся заново. Сохранённый `verification.json` — исторический результат
проверки от 7 октября, а не отчёт о текущем запуске тестов.

Из каталога проекта:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e .
cp .env.example .env
```

В `.env` впишите полный базовый URL своего вебхука в `BITRIX_WEBHOOK_URL`.
Реальный токен в проект не включён. Вебхук действует от имени своего владельца;
используется CRM REST, отдельный OAuth токен для этой реализации не нужен.
Вебхук и права CRM должны оставаться действительными.

| Настройка | Значение по умолчанию |
|---|---|
| `BITRIX_TIMEZONE` | `Europe/Moscow` |
| `BITRIX_STATE_PATH` | `.state/operations.sqlite3` |
| `BITRIX_ALLOW_WRITES` | `false` |
| `BITRIX_TIMEOUT` | 20 секунд |
| `BITRIX_READ_RETRIES` | 2 повторения только запросов чтения |

Файл окружения не переопределяет уже заданные переменные среды. Пути настроек и
журнала относительны текущему рабочему каталогу. Для будущего бота и нескольких
процессов задайте **один абсолютный путь** журнала на общем локальном диске.
`.env`, журнал и служебные файлы исключены из Git.

## Проверка через консоль

```bash
bitrix-time check
bitrix-time day --date 2026-10-05
bitrix-time entries --date 2026-10-05
bitrix-time remote-list --date 2026-10-07
bitrix-time contracts 'Пример карточки' --type 1298
```

Все даты вводятся как `YYYY-MM-DD`, время — локальное `HH:MM`.
Интервал должен завершаться позже начала в пределах одной даты.
Длительность учета времени: целые часы плюс 0 или 30 минут, от 30 минут до 24 часов.

Предварительная проверка удалёнки:

```bash
bitrix-time remote --date 2026-10-19 --from 09:00 --to 18:00 \
  --comment 'Работа над проектом'
```

Обычный рабочий день вручную:

```bash
bitrix-time workday --date 2026-10-19 --from 09:00 --to 18:00
```

Учет времени в существующем дне:

```bash
bitrix-time entry --date 2026-10-05 \
  --contract-type 1298 --contract-id 123 \
  --description 'Работа по задаче' --hours 7 --minutes 30
```

Без `--apply` эти команды выполняют только чтение и возвращают `status: preview`
с точными полями будущего запроса. Если найдена совпадающая запись, результат
содержит её ID. Предварительная проверка не создает файл журнала.

**Для реального сохранения** добавьте `--apply` к конкретной команде. Этот флаг
разрешает запись для одного запуска независимо от `BITRIX_ALLOW_WRITES` в `.env`.
Для CLI переменная `BITRIX_ALLOW_WRITES=true` сама по себе запись не включает.
Можно добавить `--idempotency-key 'manual:remote:2026-10-19'`.

Альтернативный запуск: `python -m bitrix_time_manager ...`.
Другой файл настроек: `bitrix-time --env-file /path/to/.env check`.
Успех возвращает JSON и код 0, ошибка — JSON в stderr и код 2.

## Использование из Python и будущего бота

```python
import asyncio

from bitrix_time_manager import BitrixClient, RemoteWorkCreate, Settings, TimeManager


async def main():
    settings = Settings.from_env()
    async with BitrixClient(settings) as client:
        manager = TimeManager(client)
        result = await manager.create_remote_work(
            RemoteWorkCreate.model_validate({"day": "2026-10-19", "start": "09:00", "end": "18:00"}),
            dry_run=True,
            idempotency_key="telegram:job:123",
        )
        print(result.model_dump(mode="json"))


asyncio.run(main())
```

Готовый пример: `python examples/python_preview.py`.
Аналогично вызываются `create_workday(WorkdayCreate(...))` и
`create_time_entry(TimeEntryCreate(...))`. Для Python запись требует
`settings.allow_writes=True` и `dry_run=False`.

Класс `TimeManager` не зависит от Telegram. Его можно переиспользовать в
обработчиках бота и заданиях расписания через прямые вызовы Python API.
Держите один `BitrixClient` на время работы приложения и закрывайте его при
завершении. Периодические задания должны иметь стабильные параметры и ключ,
например `auto:remote:500:2026-10-19`. Изменение параметров уже выполненного
задания требует отдельного решения пользователя. Сам бот и расписание в эту
версию не включены.

## Поведение портала и повторных запросов

Удалёнка создаётся отдельно. Привязку рабочего дня выполняют роботы Bitrix.
API не создает дополнительный день вслед за удалёнкой. Если `workday_id` ещё
пустой, позднее вызовите `get_workday(date)`; добавление учета времени станет
возможным после появления дня. Для ручного обычного дня устанавливаются
«Рабочий день» и источник «Другое».

Запись учета времени требует существующего дня и доступного договора. Для
отсутствующего дня операция завершается ошибкой. Идентификатор договора — ID
карточки плюс тип процесса, а не текстовый номер договора. Доступные типы договорных
карточек: 1048 и 1052; тип 1298 — шаблоны. Поиск помогает выбрать карточку.
Подтвержденный пример: тип 1298, ID 123 — «Пример карточки».

API сверяет уже существующие записи, включая созданные вручную. Совпадающие
параметры возвращают `status: existing`; другой рабочий день за ту же дату или
пересечение удалёнки дают конфликт. Последовательные непересекающиеся интервалы
удалёнки разрешены. Одинаковые записи учета времени считаются одной операцией.

Перед записью SDK сохраняет операцию в SQLite. В Bitrix передается стабильный
`xmlId`, рассчитанный по порталу, сотруднику, типу операции и параметрам.
`crm.item.add` отправляется **один раз**: автоматических повторов записи нет.
Если ответ потерян, повтор того же запроса ищет созданную запись и возвращает
`existing`. Если запись не найдена, автоматическая отправка блокируется:
потерянный ответ не доказывает, что создание не состоялось.

```bash
bitrix-time journal
# Только после ручной проверки, что операция действительно ничего не создала:
bitrix-time resolve OPERATION_ID --confirmed-not-created
```

Сохранённая успешная операция, запись которой удалили вручную, также не
отправляется заново. Не удаляйте журнал, чтобы обойти блокировку.
Для нескольких процессов нужен один журнал. Bitrix не гарантирует уникальность
`xmlId`: независимые журналы на разных машинах не обеспечивают защиту от гонки.

Общий журнал резервирует одинаковую операцию, но проверка пересечений разных
интервалов удалёнки не атомарна. Одновременные запросы с разными параметрами
могут пройти проверку до появления другой карточки. До исправления этого
ограничения такие операции для одного сотрудника выполняйте последовательно.

Код использует проверенную схему конкретного портала: процессы 1208, 1218, 1250
и пользовательские поля. Это не стандартный `timeman.open`. При отсутствии или
несовместимости ожидаемых полей проверка блокирует операции; актуализируйте
`PortalSchema` в `config.py`.
Для другого портала потребуется отдельная сверка схемы. Перед первым применением
проверьте `check`, затем предварительный результат и один выбранный запрос
создания вручную; после сохранения проверьте поля, связанный день и роботов.

## Проверки разработки

```bash
python -m pip install -e '.[dev]'
python -m pytest -q
python -m ruff check src tests examples
python -m ruff format --check src tests examples
python -m mypy src
```

По умолчанию выполняется весь offline-набор; обращения к реальному Bitrix
заблокированы на уровне HTTP-транспорта. Настройки тестов не наследуют рабочий
вебхук или разрешение записи из окружения. SQLite создаётся во временных каталогах.

| Уровень | Каталог и маркер | Проверки |
|---|---|---|
| Unit | `tests/unit`, `unit` | Валидация моделей, настройки окружения, маскировка секретов и ошибки |
| Mock | `tests/mock`, `mock` | REST-клиент с `httpx.MockTransport`: повторы, лимиты, ошибки сети, JSON и пагинация; ответы сервиса, схема и принадлежность дня |
| Integration | `tests/integration`, `integration` | Реальные SDK-компоненты и SQLite, жизненный цикл операций, перезапуски, несколько клиентов, конкурирующие процессы и CLI |
| Live integration | `tests/integration/test_live_portal.py`, `integration` и `live` | Реальный Bitrix: чтение профиля, схемы, дня, учета, удалёнки и поиск договоров |

Offline-интеграционные тесты используют настоящую SQLite и отдельные процессы,
а границу Bitrix заменяют управляемой моделью портала. Они проверяют дубли,
конфликты, потерю ответа, отмену записи, сохранение полученного ID, восстановление
после перезапуска и разделение операций разных клиентов. Проверка резервирования
между процессами не гарантирует атомарную защиту разных пересекающихся интервалов
удалёнки — ограничение описано выше.

### Отчёты и обязательное покрытие

Команда `python -m pytest -q` автоматически формирует:

| Файл | Содержание |
|---|---|
| `reports/coverage/index.html` | HTML-отчёт с покрытием по файлам, строкам и ветвям |
| `reports/coverage.xml` | Покрытие в формате Cobertura для CI |
| `reports/coverage.json` | Машиночитаемая статистика покрытия |
| `reports/junit.xml` | Результаты тестов, ошибки и время выполнения в формате JUnit |

В консоли выводится сводка с непокрытыми строками. Учитывается весь пакет,
включая CLI и `__main__.py`; покрытие отдельных процессов собирается автоматически.
Порог **90% применяется к общей метрике строк и ветвей coverage.py**.
Это не отдельная гарантия 90% для каждого файла или каждого вида тестов.
Недостаточное покрытие завершает запуск с ненулевым кодом даже при успешных тестах.
Отчёты исключены из Git и обновляются при запуске.

Отдельные уровни можно запускать без проверки общего покрытия:

```bash
python -m pytest -q -m unit --no-cov
python -m pytest -q -m mock --no-cov
python -m pytest -q -m 'integration and not live' --no-cov
```

Эти команды обновляют JUnit, но не обновляют отчёты покрытия; полный свежий
отчёт получается после обычного запуска всего offline-набора.

GitHub Actions запускает offline-набор, Ruff и mypy на Python 3.11–3.14.
HTML/XML/JSON/JUnit-отчёты сохраняются в artifacts для каждой версии Python,
в том числе при падении тестов, если отчёты успели сформироваться.

### Проверка реального портала

Live-тесты по умолчанию исключены. Они используют только явно заданный
`BITRIX_TEST_WEBHOOK_URL`, не загружают рабочий `.env` и всегда отключают запись.
Выполняются только чтения; `crm.item.add` не вызывается.

Задайте тестовый вебхук в окружении безопасным способом, затем выполните:

```bash
python -m pytest -q -m live --no-cov
```

Без `BITRIX_TEST_WEBHOOK_URL` выбранные live-тесты пропускаются.
Дополнительные переменные: `BITRIX_TEST_TIMEZONE` (по умолчанию `Europe/Moscow`),
`BITRIX_TEST_DAY` (`YYYY-MM-DD`, по умолчанию сегодня в выбранной зоне),
`BITRIX_TEST_CONTRACT_QUERY` (по умолчанию `Пример`).
Проверки ожидают поддерживаемую схему портала. Работу роботов после реального
создания и граничные правила дат этот набор не подтверждает.

[crm.item.add](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-add.html),
[crm.item.list](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-list.html).
