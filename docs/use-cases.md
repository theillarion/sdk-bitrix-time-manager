# Use-case Python SDK и CLI

Дата: **8 октября 2026 года**. Версия: **0.1.0**.
Связанные документы: [требования](technical-requirements.md),
[чек-листы](checklists.md), [ограничения](limitations.md).

Участники: приложение, вызывающее Python SDK; оператор CLI; Bitrix;
локальный журнал. Приложение может быть Telegram-ботом, но транспортом
интеграции остаётся прямой вызов Python-методов.

Условия записи: валидированные данные, действующий вебхук и права Bitrix,
совместимая схема, исправный общий журнал, явное разрешение записи.
Автоматические проверки сценариев выполняются с mock-транспортом и временной БД.
Правила приложения проверяются до вызова SDK.

## UC-01. Установить SDK и запустить CLI

**Связь:** TR-01, TR-02, NFR-04. **Участник:** разработчик.

**Предусловия:** Python 3.11+, отдельное окружение, доступ к пакету/репозиторию.

1. Установить пакет из каталога SDK через `python -m pip install -e .`
   либо установить подготовленный wheel.
2. Импортировать `Settings`, `BitrixClient`, `TimeManager`.
3. Выполнить `bitrix-time --help` и `python -m bitrix_time_manager --help`.
4. Подключить SDK к приложению как зависимость с закреплённым коммитом/версией.

**Альтернативы:** отсутствует подходящий Python или зависимость — установка
завершается ошибкой; импорт из старого checkout требует исправить окружение.

**Приёмка:** обе точки входа CLI доступны, импорты относятся к установленному
SDK; для справки не нужны вебхук, журнал или запрос к Bitrix.

## UC-02. Подключиться и проверить схему

**Связь:** TR-03, TR-04. **Участник:** приложение/оператор.

**Предусловия:** собственные настройки и действующий вебхук.

1. Создать `Settings` либо загрузить настройки из заданного файла.
2. Открыть `BitrixClient` как async context manager.
3. Создать `TimeManager` и вызвать `check_connection()`; для CLI — `bitrix-time check`.
4. Получить портал без секрета, ID владельца, зону, результат проверки полей
   и информацию о доступности метода добавления.

**Альтернативы:** неверный URL/пояс → `ConfigurationError`; несовпадение профиля
или схемы → `SchemaError`; отказ Bitrix/сети → соответствующее исключение.

**Приёмка:** `crm.item.add` не вызывается. Успех не трактуется как подтверждение
права создания карточки, совместимости любого портала или времени работы роботов.

## UC-03. Посмотреть день, учет времени и удалёнку

**Связь:** TR-06. **Участник:** приложение/оператор.

**Предусловия:** дата и подключение владельца вебхука.

1. Вызвать `get_workday(day)` / CLI `day --date YYYY-MM-DD`.
2. При наличии дня вызвать `list_time_entries(day)` / `entries --date ...`.
3. Независимо от наличия дня вызвать `list_remote_work(day)` / `remote-list --date ...`.
4. Отобразить выбранные данные в интерфейсе приложения.

**Альтернативы:** отсутствие дня → `None` при чтении дня, `NotFoundError` при
чтении учета; несколько дней → `ConflictError`; отсутствие удалёнки → `[]`.
Для периода приложение повторяет чтение по датам.

**Приёмка:** день относится к владельцу вебхука; учет привязан к его дню;
удалёнка отбирается по ответственному и дате начала. Запись не выполняется.

## UC-04. Найти договор или шаблон

**Связь:** TR-07. **Участник:** приложение/оператор.

**Предусловия:** фрагмент названия и один тип `1048` / `1052` / `1298`.

1. Вызвать `search_contracts(query, entity_type_id=..., limit=...)`;
   CLI: `contracts 'Пример карточки' --type 1298 --limit 20`.
2. Получить ID, название и тип найденных карточек.
3. Выбрать карточку и сформировать `ContractRef` для учета времени.

**Альтернативы:** пустой запрос/неподдерживаемый тип/limit вне 1–100 → `ValueError`;
нет результатов → `[]`; карточка стала недоступна — создание учета позже откажет.

**Приёмка:** выполняется поиск в выбранном типе; SDK не подменяет ID карточки
текстовым номером договора и не обещает ссылку как поле `ItemSummary`.

## UC-05. Предварительно проверить создание

**Связь:** TR-05, TR-08, TR-13. **Участник:** приложение/оператор.

**Предусловия:** валидированная модель одной из двух операций.

1. Вызвать соответствующий `create_*()` с `dry_run=True` либо оставить значение
   по умолчанию; CLI запустить без `--apply`.
2. Дождаться проверки схемы, нужных связей и совпадающих карточек.
3. Получить `OperationResult(status='preview')` с полями и ID операции.
4. При наличии совпадения получить ID/ссылку существующей карточки.

**Альтернативы:** несовместимая схема, недоступный договор, отсутствующий день
для учета или конфликт останавливают предварительную проверку.

**Приёмка:** нет `crm.item.add` и создания журнала. Переданный caller key не
привязывается; preview не даёт гарантии будущего успеха и не резервирует запуск.

## UC-07. Добавить учет времени в существующий день

**Связь:** TR-05, TR-09, TR-11. **Участник:** приложение/оператор.

**Предусловия:** собственный день существует, договор доступен, длительность
и описание допустимы, запись разрешена SDK и приложением.

1. Сформировать `TimeEntryCreate` с датой, `ContractRef`, описанием и длительностью.
2. Вызвать `create_time_entry(..., dry_run=False, idempotency_key=...)`
   либо CLI `entry ... --apply --idempotency-key ...`.
3. SDK проверяет день/договор, совпадения, сохраняет намерение и добавляет карточку.
4. Получить ID, ссылку и `workday_id`; приложение сообщает результат.

**Альтернативы:** нет дня → `NotFoundError`, без создания дня; недоступен договор →
ошибка Bitrix; совпадение → `existing`; неизвестный результат → UC-10.

**Приёмка:** связь с найденным днём, правильный CRM-код договора и справочник
минут. SDK проверяет длительность отдельной записи, а не сумму за день.

## UC-08. Создать удалённую работу

**Связь:** TR-09, TR-12. **Участник:** приложение/оператор.

**Предусловия:** дата и положительный интервал одной даты, запись разрешена.
Допустимость целевой даты по правилам компании проверило приложение.

1. Сформировать `RemoteWorkCreate` и вызвать `create_remote_work(..., dry_run=False)`;
   CLI: `remote ... --apply`.
2. SDK последовательно сверяет дубль, пересечения и незавершённые интервалы.
3. При отсутствии конфликта сохраняет намерение и отправляет одно добавление.
4. Возвращает ID и ссылку; при отсутствии связанного дня — предупреждение.
5. Приложение позже читает день через `get_workday(day)`, если он нужен.

**Альтернативы:** совпадение → `existing`; отличающийся пересекающийся интервал
или незавершённый интервал той же даты → `ConflictError`. Соседний непересекающийся
интервал допустим. Параллельные разные интервалы имеют ограничение LIM-01.

**Приёмка:** SDK не создаёт обычный день вслед за удалёнкой и не обещает время
роботов. Пустой `workday_id` не означает неуспешное создание самой удалёнки.

## UC-09. Повторить запрос без дубля

**Связь:** TR-13, TR-14. **Участник:** приложение/оператор.

**Предусловия:** сохранены исходные параметры и контекст операции, общий журнал.

1. Повторить тот же вызов с теми же данными и caller key, если он использовался.
2. SDK сверяет Bitrix и возвращает `existing` для подходящей карточки.
3. Журнал сохраняет подтверждённый результат.

**Альтернативы:** тот же key с другими данными → `ConflictError`; изменённая
карточка того же `xmlId` → конфликт; несколько таких карточек → конфликт.
Если успешная карточка удалена и другой подходящей карточки нет,
сохранённый успех блокирует пересоздание. Pending/uncertain без карточки → UC-10.

**Приёмка:** повтор не добавляет карточку. Разные caller keys не делают
одинаковые логические данные разными операциями; смена зоны требует LIM-06.

## UC-10. Сверить неизвестный результат записи

**Связь:** TR-14, TR-15. **Участник:** приложение/оператор.

**Предусловия:** добавление могло дойти до Bitrix; журнал исправен.

1. SDK получает тайм-аут/повреждённый ответ и сохраняет `uncertain`.
2. Выбрасывает `UncertainWriteError` с ID операции без слепого повтора добавления.
3. Потребитель повторяет исходный вызов для сверки.
4. Если карточка найдена и совпадает, SDK возвращает `existing` и фиксирует успех.

**Альтернативы:** карточка не найдена → повторное добавление блокируется;
сверка недоступна → состояние не объявляется гарантированным отказом;
карточка изменилась → конфликт. Для освобождения используется UC-11.

**Приёмка:** потерянный ответ не доказывает отсутствие карточки. Восстановление
не выдаёт `recovered`: текущий сервис возвращает `existing`.

## UC-11. Освободить операцию после ручной проверки

**Связь:** TR-14, TR-15, TR-17. **Участник:** оператор.

**Предусловия:** `pending` / `uncertain`, ручная проверка Bitrix подтверждает
отсутствие записи, нет продолжающегося отправителя этой операции.

1. Посмотреть `bitrix-time journal` и нужную карточку/дату на портале.
2. Выполнить `bitrix-time resolve OPERATION_ID --confirmed-not-created`
   либо `OperationJournal.confirm_not_created(operation_id)`.
3. Убедиться, что состояние стало `failed`; сама команда ничего не добавила.
4. Если требуется, отдельно повторить исходную операцию с явным разрешением записи.

**Альтернативы:** записи журнала нет или состояние не подходит → `ConflictError`;
результат на портале не установлен → операцию не освобождать.

**Приёмка:** журнал не удаляется для обхода защиты; очистка состояния и фактическая
запись — разные действия. Освобождение не служит подтверждением результата Bitrix.

## UC-12. Отменить запрос или завершить приложение

**Связь:** TR-02, TR-14, TR-15. **Участник:** приложение/оператор.

**Предусловия:** запрос в работе, приложение управляет async-задачей и клиентом.

1. Приложение прекращает запуск новых операций и отменяет/дожидается текущей задачи.
2. При отмене во время добавления SDK помечает неопределённость и пробрасывает
   `asyncio.CancelledError`.
3. Если ID уже сохранён, отмена проверочного чтения оставляет `succeeded`.
4. Приложение закрывает клиент и при следующем запуске сверяет незавершённое.

**Альтернативы:** аварийное завершение между резервацией и фиксацией результата
оставляет `pending`; отсутствие исправной БД требует ручной сверки.

**Приёмка:** отмена не приравнивается к отсутствию записи; повтор не выполняется
автоматически. SDK не является серверным обработчиком SIGTERM или планировщиком.

## UC-13. Одновременно выполнить одну логическую операцию

**Связь:** TR-13, TR-14, NFR-03. **Участник:** два исполнителя.

**Предусловия:** одинаковые параметры/контекст и один абсолютный путь SQLite.

1. Первый исполнитель резервирует операцию и начинает добавление.
2. Второй сверяет карточку и пытается выполнить ту же операцию.
3. Если карточка уже видна, второй возвращает `existing`; если резервация ещё
   в работе — получает `UncertainWriteError` вместо второго добавления.

**Альтернативы:** занятый SQLite может вернуть ошибку журнала; разные локальные
журналы не обеспечивают общую защиту. Разные операции, включая пересекающиеся
интервалы и разные дни с одной датой, этим сценарием не защищены.

**Приёмка:** для сценария с общим исправным журналом и одним ID выполняется
не более одной отправки добавления. Перед выпуском нужны межпроцессные проверки,
а не только две async-задачи в одном процессе.

## UC-14. Встроить SDK в Telegram-бота или другое приложение

**Связь:** TR-02, TR-03, TR-18, NFR-02. **Участник:** разработчик приложения.

**Предусловия:** приложение владеет подключением, контекстом пользователя,
разрешёнными действиями и журналом. SDK установлен как зависимость.

1. Создать собственные `Settings` для подключения и переиспользуемый клиент.
2. До записи проверить допуск, целевую дату и бизнес-правила приложения.
3. Вызвать публичный метод `TimeManager` с моделью и стабильным caller key.
4. Обработать `OperationResult` либо доменное исключение и сохранить собственное
   состояние запуска/уведомления.
5. Закрыть клиент при завершении приложения.

Минимальный пример прямого вызова без реальной записи:

```python
import asyncio

from pydantic import SecretStr

from bitrix_time_manager import BitrixClient, RemoteWorkCreate, Settings, TimeManager


async def main() -> None:
    settings = Settings(
        webhook_url=SecretStr("https://example.test/rest/500/example-secret/"),
        allow_writes=False,
    )
    spec = RemoteWorkCreate.model_validate(
        {"day": "2026-10-19", "start": "09:00", "end": "18:00"}
    )
    async with BitrixClient(settings) as client:
        result = await TimeManager(client).create_remote_work(spec, dry_run=True)
        print(result.status)


if __name__ == "__main__":
    asyncio.run(main())
```

Пример содержит вымышленный URL; для выполнения нужны собственное подключение
или mock-транспорт. Запуск примера всё равно выполняет чтение через сеть.

**Альтернативы:** неподдерживаемый портал → отказ проверки; несколько пользователей
нельзя подключать изменением общего `.env`; низкоуровневый вызов требует своего guard.

**Приёмка:** интеграция вызывает Python-методы в том же процессе, не требует
промежуточного HTTP-сервера и не использует приватные методы `TimeManager`.
SDK не поддерживает ручное создание рабочего дня — день появляется по отметке
СКУД или роботами удалённого дня; SDK не реализует регистрацию, предупреждения
и расписания вместо приложения.
