# Технические требования к Python SDK Bitrix Time-manager

Дата: **8 октября 2026 года**. Основание: версия **0.1.0** и её исходники.
Навигация: [каталог](README.md), [use-case](use-cases.md),
[чек-листы](checklists.md), [ограничения](limitations.md).

## 1. Назначение и границы

SDK обеспечивает чтение и создание карточек учета времени, рабочего дня и
удалённой работы на совместимом Bitrix через входящий вебхук. Поддерживаемый
профиль по умолчанию относится к исходному корпоративному порталу. Это CRM
смарт-процессы, а не стандартные методы `timeman.*`.

Потребители: Python-приложение и оператор CLI.
Bitrix определяет права владельца вебхука и поведение своих роботов.

Telegram-бот использует `TimeManager` напрямую. Рабочий день создаётся
порталом автоматически (проход СКУД или робот удалённого дня); ручное создание
дня SDK не поддерживает. Проверку допуска, сроков дат, календаря и управления
расписаниями выполняет приложение.

## 2. Архитектура и поставка

### TR-01. Самостоятельный Python-пакет

Пакет должен устанавливаться из своего каталога и собираться в wheel.
Имя дистрибутива — `bitrix-time-manager`; импорт — `bitrix_time_manager`;
минимальная заявленная версия Python — 3.11. CLI устанавливается как
`bitrix-time`; эквивалентный запуск — `python -m bitrix_time_manager`.

Основные зависимости: `httpx`, `pydantic`, `python-dotenv`. Инструменты
разработки подключаются через extra `dev`. Базовые импорты SDK не должны
требовать Telegram или запущенного HTTP-сервера.
Заявленная нижняя версия Python не означает, что весь диапазон уже проверен в CI.

### TR-02. Прямой API и жизненный цикл

Публичные экспорты корня пакета: `BitrixClient`, `Settings`, `PortalSchema`,
`TimeManager`, `ContractRef`, `RemoteWorkCreate`, `TimeEntryCreate`,
`OperationResult`.
`Workday` и `ItemSummary` доступны в `bitrix_time_manager.models`,
`OperationJournal` — в `bitrix_time_manager.journal`, исключения — в `errors`.

Сервис не должен зависеть от CLI или Telegram. Сетевые методы выполняются
через `await`. Приложение переиспользует HTTP-клиент на время своего жизненного
цикла и закрывает его через `async with` или `aclose()`.
Методы с префиксом `_` не являются интерфейсом интеграции.

## 3. Конфигурация и схема

### TR-03. Проверяемые настройки

`Settings` должен принимать базовый HTTPS URL вида
`https://example.test/rest/500/example-secret/`, именованный часовой пояс,
путь журнала, тайм-аут, число повторов чтения и разрешение записи.
В примерах используются только искусственные секреты.

| Настройка | По умолчанию | Проверка |
|---|---|---|
| `BITRIX_WEBHOOK_URL` | Нет | HTTPS, непустой hostname, путь `/rest/<положительный ID>/<секрет>/`; без userinfo, query и fragment |
| `BITRIX_TIMEZONE` | `Europe/Moscow` | Доступна через `ZoneInfo` |
| `BITRIX_STATE_PATH` | `.state/operations.sqlite3` | Относится к рабочему каталогу процесса; доступность проявляется при обращении к журналу |
| `BITRIX_TIMEOUT` | `20` | `0 < timeout <= 120` секунд |
| `BITRIX_READ_RETRIES` | `2` | Целое число от 0 до 5 |
| `BITRIX_ALLOW_WRITES` | `false` | `true` / `false` / `1` / `0` |

`Settings.from_env()` читает `.env` относительно рабочего каталога, если файл
не задан иначе, и не переопределяет существующие переменные среды.
`env_file=None` исключает загрузку файла; аргумент `allow_writes` переопределяет
соответствующий флаг. Для разных пользователей приложение создаёт отдельные
объекты `Settings`, а не последовательно загружает их `.env` в общую среду.
Проверка формата URL не является защитой от SSRF: [LIM-04](limitations.md#lim-04-проверка-url-и-секреты).

### TR-04. Поддерживаемая схема и проверка подключения

| Назначение | `entityTypeId` | Категория для создания |
|---|---|---|
| Рабочий день | ID смарт-процесса дней | ID категории дня |
| Учет времени | ID смарт-процесса учета | ID категории учета |
| Удалённая работа | ID смарт-процесса удалёнки | ID категории удалёнки |
| Договорные карточки / шаблоны | `1048`, `1052`, `1298` | SDK не создаёт их через `TimeManager` |

Точное соответствие пользовательских полей, видов дня, источника и минут
определяет [PortalSchema](../src/bitrix_time_manager/config.py).
`check_connection()` должен сверить `profile.ID` с ID из URL, проверить поля
трёх типов и прочитать доступность `crm.item.add` через `method.get`.
Создание карточек в этой проверке не выполняется.

Перед подготовкой создания проверяются ожидаемые поля нужного типа: наличие,
тип и отсутствие признака read-only; для учета — справочник минут и разрешённые
договорные типы. Успешная проверка типа кэшируется в экземпляре `TimeManager`.
Она не повторяется перед каждым запросом и не проверяет все настройки роботов,
категорий или прав записи. Получение профиля выполняется в `check_connection()`,
а не автоматически при каждом создании. Другой hostname не доказывает
совместимость схемы: [LIM-05](limitations.md#lim-05-схема-и-корпоративные-правила).

## 4. Данные и операции

### TR-05. Валидация моделей

Модели должны отклонять неизвестные поля и запрещать присваивание их атрибутов
после создания. Это не глубокая неизменяемость вложенных `dict` и `list`.

- Интервал: одна дата, локальные начало и конец, конец строго позже начала.
  Часовой пояс в значении времени и ненулевые секунды/микросекунды запрещены.
  Комментарий — до 4000 символов. Ночные интервалы не поддерживаются.
- Договор: тип `1048`, `1052` или `1298`, положительный ID карточки.
  CRM-ссылка кодирует тип в шестнадцатеричном виде: тип `1000`, ID `7` → `T3E8_7`.
- Учет: непустое описание до 4000 символов с обрезкой крайних пробелов;
  целые часы 0–24 и минуты 0 либо 30; сумма от 30 минут до 24 часов.
  Для `hours` включена строгая проверка целого числа.
- Поля даты и времени используют преобразования Pydantic. Рекомендуемый
  внешний формат — `YYYY-MM-DD` и `HH:MM`; модели не вводят строгий строковый
  формат для всех входов.

При формировании datetime используется зона из `Settings`, а не зона хоста.
Несуществующее время при переходе DST отклоняется; неоднозначное время и смена
зоны между повторами имеют ограничения из [LIM-06](limitations.md#lim-06-идентичность-операции-и-время).

### TR-06. Чтение собственных данных

| Метод | Результат и особые условия |
|---|---|
| `get_workday(day)` | `Workday` или `None`; несколько дней на дату → `ConflictError`; сверяются дата и сотрудник |
| `list_time_entries(day)` | `list[dict]` с явно выбранными полями; собственный день и категория учета; отсутствие дня → `NotFoundError` |
| `list_remote_work(day)` | `list[dict]`; ответственный — владелец вебхука, начало в пределах локальной даты; пустой список допустим |

Список удалёнки показывает интервалы, **начинающиеся** в целевую дату.
Это не выборка всех интервалов, пересекающих дату. Обход периода выполняет
приложение; отдельного метода периода нет.

### TR-07. Поиск договора

`search_contracts(query, entity_type_id=1298, limit=20)` должен искать по фрагменту
названия в одном разрешённом типе. Запрос после `strip()` непустой; limit 1–100.
Возвращается `list[ItemSummary]` с ID, названием и типом. Поле ссылки в этой
модели отсутствует. Перед созданием учета SDK проверяет доступность выбранной
карточки через `crm.item.get`, получая полную карточку.

### TR-08. Предварительная проверка

Оба метода создания имеют `dry_run=True` по умолчанию. Сервис выполняет
чтение, проверку схемы, необходимых связей и дублей, возвращая `preview`
с точными полями предполагаемого добавления и стабильным ID операции.
Найденный дубль добавляет ID/ссылку карточки, но статус остаётся `preview`.

Preview не отправляет `crm.item.add`, не создаёт журнал и не привязывает
`Idempotency-Key`. Поэтому успешный preview не резервирует операцию и не
гарантирует отсутствие конфликтов или наличие прав в момент будущей записи.

### TR-09. Явное разрешение записи и результат

Для Python нужны `settings.allow_writes=True` и `dry_run=False` одновременно.
Режим предварительной проверки и режим записи должны различаться явно.

`OperationResult` содержит статус, вид операции, `operation_id`, тип процесса,
ID/ссылку карточки, ID дня, подготовленные поля и предупреждения.
Сервис фактически выдаёт `preview`, `created`, `existing`.
`recovered` разрешён моделью, но сейчас не используется: восстановление найденной
карточки возвращает `existing`. Предупреждение не отменяет полученный ID создания.

### TR-11. Учет времени

`create_time_entry(TimeEntryCreate(...))` должен найти собственный день,
проверить договор и добавить запись в смарт-процесс учета со связью на процесс
рабочего дня (`parentId<ID процесса дня>`). Минуты кодируются значениями
справочника минут (0 и 30).
Если дня нет, создание заканчивается `NotFoundError` без добавления карточки.
Рабочий день автоматически не создаётся. Сумма всех записей за день не
ограничивается SDK: проверяется длительность одной записи.

### TR-12. Удалённая работа

`create_remote_work(RemoteWorkCreate(...))` добавляет запись удалённой работы:
начало, конец и комментарий. Ответственным назначается владелец вебхука.
Поле `remote_employee` и связь с днём в запрос не включаются.

Создание/привязка дня остаётся за роботами Bitrix. Пустой `workday_id` после
создания допустим и сопровождается предупреждением; SDK не создаёт второй день
и не ждёт роботов циклическими запросами. Перед записью последовательно
проверяются совпадения и пересечения; соприкасающиеся интервалы допустимы,
незавершённый интервал на той же дате считается конфликтом.
Параллельные разные интервалы требуют учёта [LIM-01](limitations.md#lim-01-гонка-разных-операций).

## 5. Дубли и восстановление

### TR-13. Идентичность и повторные запросы

ID операции вычисляется SHA-256 от нормализованных входных данных, вида операции,
портала и сотрудника. В Bitrix передаётся `xmlId=btm_<operation_id>`.
Одинаковые логические данные дают один ID даже при разных caller keys.

Перед добавлением SDK ищет карточку по `xmlId` и ответственному, затем по
основным данным операции. Изменённые поля карточки с этим `xmlId` и несколько
карточек с одним `xmlId` считаются конфликтом. Поиск также распознаёт совпадающие
ручные записи. Повтор одинакового учета времени считается одной операцией.

`Idempotency-Key`, если задан, имеет длину 1–200 символов, ограничен порталом
и сотрудником, хранится в виде хеша и привязывается к одному ID операции.
Повтор ключа с другим содержимым при реальном выполнении вызывает конфликт.
Для устранения дубля Bitrix сам по себе не обязан обеспечивать уникальность `xmlId`.

### TR-14. Журнал до внешней записи

До `crm.item.add` должна быть зафиксирована транзакционная резервация операции
в SQLite. Таблицы: `operations` и `request_keys`. Переходы:

| Состояние | Смысл | Разрешённое продолжение |
|---|---|---|
| `pending` | Резервация сохранена; отправка могла начаться | Сверка; без автоматического повторного добавления |
| `uncertain` | Ответ не позволяет установить результат | Сверка; при отсутствии карточки повтор блокируется |
| `failed` | Явный отказ либо подтверждённое оператором отсутствие | Новая попытка с теми же данными допустима |
| `succeeded` | Получен ID либо найдена подходящая карточка | Вернуть существующую; исчезновение карточки не разрешает её пересоздать |

После ответа с ID результат сохраняется до проверочного чтения.
Если повтор находит созданную карточку, журнал переводится в `succeeded`.
Журнал хранит JSON результата, включая поля запроса и рабочие тексты; он не
ограничен техническими ID. Встроенного срока очистки или шифрования нет.
Резервация одинакового ID сериализуется между процессами с одним журналом;
разные журналы или разные ID не дают общей гарантии уникальности.

### TR-15. Неизвестный результат и отмена

`crm.item.add` отправляется один раз на попытку. Тайм-аут, повреждённый ответ
добавления без положительного ID или неоднозначный HTTP-ответ приводят к
`uncertain` и `UncertainWriteError` при исправном журнале.
Ответ Bitrix с явной ошибкой и HTTP < 500 сохраняет `failed`; HTTP >= 500 —
`uncertain`. Последняя классификация отражает текущую реализацию.

Отмена во время запроса должна сохранить неопределённость и повторно выбросить
`asyncio.CancelledError`. Отмена после сохранения известного ID не стирает успех.
Сбой записи в сам журнал требует отдельной сверки: универсальная гарантия
сохранения невозможна при неисправном хранилище.

`confirm_not_created()` допускается только для `pending` / `uncertain` после
ручной проверки отсутствия карточки; переводит в `failed`, но не отправляет запись.
Проверочное чтение после добавления может вернуть предупреждение об изменении
полей роботами или невозможности прочитать карточку без повторного добавления.

## 6. Транспорт и интерфейсы

### TR-16. Сеть, повторы чтения и страницы

Разрешённые имена методов клиента: `profile`, `method.get`, `crm.item.fields`,
`crm.item.get`, `crm.item.list`, `crm.category.list` и `crm.item.add`.
Любой другой метод отклоняется до отправки. Параметры и типы низкоуровневого
`call()` не образуют полноценный allowlist: [LIM-02](limitations.md#lim-02-границы-низкоуровневого-клиента).

HTTP-клиент использует HTTPS, тайм-аут и отключённые редиректы. Для чтения
выполняется не более `read_retries + 1` попыток при transport error, HTTP 429,
HTTP >= 500 либо `QUERY_LIMIT_EXCEEDED`. Пауза — `0.3 * 2**attempt` секунд.
Другие API-ошибки не повторяются. Повторов добавления нет; поддержки
`Retry-After` и jitter сейчас нет.

`list_items()` собирает страницы с сортировкой `id ASC` до исчерпания `next`
или limit, проверяет формат списков и элементов, ловит повтор курсора.
По умолчанию выбираются `['*']`; явный `select` задаёт вызывающий код.
Это сбор списка в памяти, а не потоковый iterator. Глобального ограничителя
частоты запросов и ограничения общего размера выборки нет.

### TR-17. CLI

Чтение: `check`, `day`, `entries`, `remote-list`, `contracts`, `journal`.
Создание: `entry`, `remote`; без `--apply` выполняется preview.
Флаг `--apply` разрешает запись для конкретного запуска; переменная
`BITRIX_ALLOW_WRITES=true` сама по себе не превращает CLI preview в запись.
Восстановление: `resolve OPERATION_ID --confirmed-not-created`.

Успех приложения: JSON в stdout, код 0. Обрабатываемая ошибка выполнения:
JSON с `error` и `detail` в stderr, код 2. `KeyboardInterrupt`: текстовая подсказка
и код 130. Ошибки разбора аргументов обрабатывает `argparse`: текстовая usage/error
и код 2, а не JSON. Команды журнала тоже загружают и проверяют `Settings`.

### TR-18. Встраивание в приложение

Приложение должно вызывать публичные методы `TimeManager` с валидированными
моделями и обрабатывать результат/исключения в своём интерфейсе. Промежуточный
REST API SDK для этой интеграции не требуется.

Для каждого подключения используются собственные `Settings` и `BitrixClient`.
Данные вебхука не выбираются из произвольного callback. Для повторной операции
сохраняются входные параметры, зона и caller key. Несколько исполнителей одной
операции используют один журнал с абсолютным путём.

Допуск пользователя, календарь, корпоративные сроки и предупреждения проверяет
приложение непосредственно перед вызовом записи. Для бота разрешены только
учет времени и удалёнка. Низкоуровневые `call()` / `get_item()` не заменяют
проверку принадлежности карточки и разрешённых параметров в приложении.

## 7. Качество и сопровождение

### NFR-01. Проверяемые контракты

Публичные функции должны иметь аннотации типов; входные DTO — валидацию.
Доменные ошибки наследуют `TimeManagerError`, транспортные ошибки скрывают
исходный URL в цепочке исключений. Это не обещание преобразовать любой
повреждённый ответ или ошибку SQLite в доменное исключение: [LIM-07](limitations.md#lim-07-ошибки-и-асинхронность).

| Исключение | Машинный `code` | Значение для потребителя |
|---|---|---|
| `ConfigurationError` | `configuration_error` | Исправить настройки |
| `BitrixAPIError` | `bitrix_api_error` | Bitrix вернул ошибку; дополнительно доступны `api_code` и `outcome_unknown` |
| `TransportError` | `transport_error` | Ответ чтения/низкоуровневого вызова не получен или некорректен |
| `SchemaError` | `schema_error` | Несовместимая схема или проверенный неверный формат ответа |
| `NotFoundError` | `not_found` | Не найден требуемый день; SDK не создаёт его неявно |
| `ConflictError` | `conflict` | Неоднозначность, конфликт данных, key или обработанная проблема журнала |
| `WritesDisabledError` | `writes_disabled` | Запись либо метод не разрешены SDK |
| `UncertainWriteError` | `uncertain_write` | Требуется сверка по доступному `operation_id`; слепой повтор запрещён |

Ошибки моделей Pydantic, `ValueError` параметров и `asyncio.CancelledError`
не являются подклассами `TimeManagerError`. Приложение должно различать их;
отмену не следует превращать в доменный отказ или подтверждение отсутствия записи.

### NFR-02. Данные и секреты

Секреты не должны попадать в примеры, Git и штатные сообщения об ошибках.
SDK использует `SecretStr` и маскировку пути вебхука в собственных ошибках
и фильтрах логирования. Это не шифрование `.env`, SQLite или резервных копий.
Приложение управляет правами файлов, защитой рабочих текстов, сроками хранения
и обработкой своих логов. Полные ответы `crm.item.get` и части списков могут
содержать больше данных, чем использует конкретный сценарий.

### NFR-03. Границы надёжности

При исправном журнале повтор одинаковой операции и потеря ответа не должны
приводить к слепому повтору добавления. Перед эксплуатацией нескольких процессов
назначается общий абсолютный путь журнала и учитывается `timeout=0` SQLite.
Общие транзакции с Bitrix отсутствуют; гарантия exactly-once для любых внешних
изменений и независимых экземпляров не заявляется.

### NFR-04. Изолированные проверки

Автоматические тесты должны использовать подменённый транспорт и временный
журнал, не рабочий вебхук. Для выпуска проверяются unit/mock-сценарии,
CLI, типы, форматирование и установка wheel. Существующие тесты в основном
работают через `httpx.MockTransport`; это не интеграция с реальным Bitrix.
Порог покрытия SDK и матрица CI отдельно не определены. Требование 90% для
бизнес-логики будущего бота автоматически сюда не переносится.

### NFR-05. Изменения публичного API

При изменении импортов, сигнатур, DTO, результатов, идентичности операции,
схемы журнала или CLI требуется обновить связанные документы и проверить
повтор старой операции. Документация не утверждает выбранную политику SemVer,
миграций или поддержку всех будущих порталов; эти решения ещё нужно принять.
